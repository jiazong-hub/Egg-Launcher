## A01：回滚涉及本次并未写入的用户配置（P1）

**位置：** `ModelArtifactTransaction.cs:57` 把登记的预选配置加入快照；`:97` 起对所有快照无条件恢复。`LocalRouterSupervisor.cs:358` 的实际调用只写 BAT、Router preset 和 Catalog，也会进入该事务。

**触发：** 事务开始后，用户或其他程序编辑、删除预选 JSON；随后任一运行生成文件的写入发生异常，例如磁盘空间不足、权限或锁定问题。

**复现：** 注入生成文件异常前，把用户 JSON 改为外部新内容，事务回滚恢复了旧内容；把 JSON 删除后再注入异常，事务回滚重新创建了该 JSON。这两次注入都没有让业务操作写用户 JSON。

**影响：** 运行生成失败可撤销用户外部修改，或违反“删除配置后不自动复活”的规则。只取消 .bak 不能消除这个独立回滚入口。

**建议：** 按操作明确事务写集。单纯生成运行文件不捕获/恢复用户 JSON、模板和模型登记；确实编辑配置的事务另行管理，回滚前检查当前版本仍属于本次写入，避免覆盖外部版本。

## A02：不同进程的设置更新缺少统一读改写边界（P1）

**位置：** `MainWindow.xaml.cs:167` 使用内存 `_settings` 计算新值，再保存整个对象；`JsonSettingsStore.cs` 的信号量仅保护单个实例。`LocalEndpointMigrationCoordinator.cs:62` 可在 Agent 中提交新的 RouterPort，而主界面设置修改不使用同一更新事务。

**触发：** 主界面保留旧设置，Agent 因端口占用完成端口迁移；之后用户修改详细日志、主题、语言、启动项或其他普通设置。

**复现：** 使用同一文件的两个实际 JsonSettingsStore 实例：前台读取端口 18080；后台保存 19090；前台按现有缓存更新语义只修改 DetailedDiagnosticsEnabled 后整体保存，实际端口回到了 18080。

**影响：** 普通偏好修改可能恢复旧连接端口，继而让 settings.json、已迁移的 config.toml 和服务端点不一致。端口覆盖已复现；完整客户端断连的后果属于调用链推导，没有操作真实客户端验证。

**建议：** 统一跨进程设置更新入口，在共同锁内读取最新内容、合并指定修改并原子提交，必要时使用版本校验。应明确与模式事务锁的顺序及持有方式，避免简单嵌套现有锁而产生死锁。

## A03：前台与后台新启动的滚动检查不一致（P2）

**位置：** 主界面在 `MainWindow.xaml.cs:1645` 检查滚动证明及随后 Runtime 选项；Agent 在 `LocalRouterSupervisor.cs:334` 使用共享解析器后继续生成和启动，`ModelStartupConfiguration.ResolveAsync` 没有相应缓存准入检查。

**触发：** JSON 请求 ContextShiftEnabled=true，缓存不存在、失效或明确为 false；后台 Agent 发起冷启动。

**复现：** 写入 Supported=false 的实际能力缓存；让真实 LocalRouterSupervisor 使用替身进程和代理执行 ReconcileAsync。进程 Start 被调用一次，ContextShiftRequested 仍为 true。

**影响：** 同一配置在主界面被拒绝，后台路径却可尝试加载；具体 Runtime 可能拒绝该参数或再次禁用功能。没有使用真实模型推断其崩溃行为。

**建议：** 把新启动的能力与运行时选项准入集中到共用入口，前后台一致执行。已有会话恢复仍使用已应用快照，不应误套新启动规则而破坏正在运行的会话。

## A04：控制管道异常断连会终止监听（P2）

**位置：** `AgentControlPipe.cs:44` 读取单行命令，单次连接处理没有局部异常恢复；Agent 的 `Program.cs:218` 只创建一次 controlTask，直到退出的 finally 才等待并记录它的异常。

**触发：** 一个客户端成功连接后，在发送命令前断开。可能出现在请求取消、客户端异常退出等连接中断场景。

**复现：** 使用随机管道名启动真实 ListenForShutdownAsync，连接后立即关闭客户端。监听任务以 IOException 结束；随后正常的 RequestShutdownAsync 超时，关闭回调没有执行。

**影响：** Agent 业务循环仍可运行，但控制关闭通道已失效，可能阻止正常停止服务、退出或后续启动所需的服务停止步骤。

**建议：** 为每次连接设置命令读取边界，在局部处理断连/错误后继续接受连接；Agent 监控监听任务的异常退出。保留 CurrentUserOnly 限制，不因修复可用性放宽权限。

## A05：载入操作改变了用户保存的滚动开关（P2）

**位置：** `ProfileEditorWindow.xaml.cs:725` 将开关值设为“JSON 请求值 AND 当前证明有效”；配置保存从该控件取值（`:592`），初始化/载入完成后又将 dirty 状态清除。

**触发：** 已保存 JSON 的 ContextShiftEnabled=true，之后换了 Runtime、相关参数发生变化，或缓存缺失，使旧证明不再有效。

**复现：** 参数页显示已有配置已载入，滚动开关却为 false，未保存标记也没有出现。未操作该开关，直接执行普通保存，重新读取 JSON 后值变成了 false。

**影响：** 载入没有忠实恢复用户意图；随后保存其他参数时会无提示改变原开关。启动时禁止使用无效证明是合理保护，载入时静默改写请求值是另一回事。

**建议：** 保留请求值，并单独展示“需重新验证/不可用”。启动与保存时要求用户明确关闭或重新检测；若确需自动调整，必须显式说明并标记修改。

## A06：206 续传响应只判断状态码，不校验区间（P2）

**位置：** `HuggingFaceFileDownloadClient.cs:92` 发送 Range；`:109` 仅按 206 决定 Append；`:146` 只校验最终长度，没有确认 Content-Range.From 与续传偏移一致。

**触发：** 本地有 partial 文件，服务器/代理返回的 206 区间与请求偏移不一致，而最终拼接长度恰好等于已知大小。

**复现：** 本地 partial 为 4 字节，请求 bytes=4-；替身返回 Content-Range: bytes 0-3/8 和 4 字节内容。下载器把它追加到旧前缀，生成 8 字节目标文件并返回成功。

**影响：** 下载结果可能是重复或错误拼接的 GGUF，后续验证或模型加载失败；不能把“长度正确”当成“续传正确”。没有声称该服务器错误是 Hugging Face 的正常行为。

**建议：** 核对区间起点、终点、总长及实际字节数；区间不符或 partial 超长时安全重启下载。对可变版本补充 ETag/If-Range 或固定版本依据，避免续传不同版本内容。

## A07：外挂下载缺少建立响应及空闲接收超时（P2，源码确认）

**位置：** `MainWindow.Downloads.cs:312/343` 为 MTP、视觉下载创建无限 Timeout 的 HttpClient；`HuggingFaceFileDownloadClient` 在 SendAsync 和读取循环中仅传入外部取消令牌，没有内部建立响应或无数据接收超时。主模型 Router 下载已有独立超时逻辑，不能覆盖此路径。

**触发：** 服务器不返回响应头，或连接保持但不再发送字节。

**影响：** 任务可以一直维持下载状态，直到用户取消或程序退出；用户取消仍有令牌可用，没有发现“无法取消”的证据。本项由完整调用链确认，未进行真实断网长时试验。

**建议：** 增加响应建立和持续无数据的超时，收到新数据后重置空闲计时；不为整个正常大文件下载增加固定总时长限制。

## A08：没有实际载入文件的草稿沿用旧登记参数（P2）

**位置：** `ProfileEditorWindow.xaml.cs:205` 仅在类型不匹配时建立 CreateUnloadedDraft；缺失或损坏配置保留了登记中的旧运行字段，而 InitializeConfigurationFiles 将当前载入路径设为空。

**触发：** 模型登记仍有旧的 64K 等参数，预选 JSON 被删除或损坏，再打开参数页。

**复现：** 页面显示“当前载入配置：无”，Context 控件仍为旧登记的 64K，并非文档所述的默认草稿。

**影响：** 模型登记中的残留运行数据又成为编辑参数来源，削弱“JSON 是参数依据”的边界，可能让另存的新配置意外继承旧设置。缺失 JSON 的新启动仍会被拒绝，没有复现沿用旧 BAT 启动。

**建议：** 统一处理不可载入配置，明确提供内存默认草稿，只保留模型身份等登记元数据。需要保留旧参数时，应作为明确的恢复选择展示，不要隐式当作默认值。

## A09：预选配置恢复后，旧错误没有被重新核验（P3）

**位置：** `ProfileEditorWindow.Configurations.cs:93-102` 使用 `_registration.ConfigurationError` 决定预选状态；成功 LoadConfigurationFileAsync 更新当前文件及参数，但没有重新检查实际预选的错误状态。

**触发：** 参数页打开时预选 A 缺失，用户恢复 A，并在同一窗口载入。

**复现：** 当前载入显示“未命名”，文件存在且启动解析成功，下次启动配置仍显示“无”。

**影响：** 页面宣称的下次启动状态与实际启动依据不一致，可能引导用户进行多余的重新应用。

**建议：** 文件恢复、成功载入或页面重新激活后，重新核验实际预选文件。载入 B 不应直接清除另一个预选 A 的错误；应检查预选本身。

## 已核对的保护及限制

- 模型 ID、Alias、文件路径与卡片名称分离；本轮未发现名称修改直接改变配置身份的入口。
- 独立配置的目录约束、模型与类型匹配、资源证明映射仍有集中检查；已启用但没有有效证明的外部能力不会仅凭 JSON 声明获得准入。
- 从模型列表移除、资源移除的保留范围已有专用保护，区别于 A01 的普通运行生成事务。当前已应用模型需先实际切换才能移除。
- 已有会话使用运行快照，外部删除 JSON 不应直接破坏会话；新启动不应回退到旧生成物。A03 是另外的能力准入缺口。
- OpenAI 恢复与模型配置独立。本轮在隔离真实配置事务中先切 Local，再删除用户 JSON 并损坏资源记录，切回 OpenAI 成功。未触碰实际账户配置或卸载安装器。
- 安全代理继续限制回环地址、路由和请求头，进程管理区分自有进程，官方配置使用备份及冲突检查。现有相关回归通过；这些结果不是渗透测试或任意本地攻击安全保证。
- 沿用此前约定，不把直接双击旧 BAT 纳入本轮正式启动入口要求；不要求每次启动重新执行模型能力检测；不把视觉元数据识别或模板渲染检查扩充为完整推理验证。
