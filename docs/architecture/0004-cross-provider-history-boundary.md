# 架构决策 0004：跨 Provider 历史查阅与续聊边界

状态：v0.9.2 已采用只读互通；原任务跨 Provider 续聊方案已放弃（2026-09-24）。

## 背景与验证

Local 任务记录了创建时的 `chatgpt_local_launcher` Provider。早期返回 OpenAI 模式时移除该定义，导致客户端无法解析旧 Local 任务。第一阶段保留一个由启动器管理、未激活且不可请求的历史 Provider 定义，用户已确认 OpenAI 模式可以打开并阅读旧 Local 项目。

第二阶段曾评估在切换模式后直接用当前模型继续原任务。已安装 Codex CLI 0.153.4 的 App Server 接口允许在 `thread/resume` 显式指定 `modelProvider` 和模型，但默认恢复仍沿用任务原 Provider。受控验证显示 CLI 显式覆盖可以改变路由；Desktop 的实际任务续发路径没有可靠采用这一覆盖：对本地来源任务选择官方模型后，仍向历史 Local Provider 地址发出请求并失败。CLI 接口能力不能直接证明 Desktop 当前版本的操作路径支持跨 Provider 原任务续聊。

## 决定

- 0.9.2 保留跨模式的项目、任务历史与上下文查阅能力。
- 历史 Local Provider 仅供客户端解析旧任务，指向 `127.0.0.1:0`，不能接收推理请求；当前官方模型仍使用官方路由。
- 因此“切回 OpenAI 后恢复官方配置”指恢复官方模型、活动 Provider、请求路由和进入 Local 前的受管理设置，不要求 `config.toml` 与进入 Local 前逐字相同。历史 Provider 定义是唯一按本决策保留的 Launcher 受管例外；不能保留指向运行中 Router 的 Local 地址。
- 不修改旧任务的 rollout、索引、Provider 身份或模型元数据；不在代理层偷偷改写请求目标。
- 原任务跨 Provider 续聊的第二阶段停止实施。本地来源任务在 OpenAI 模式、官方来源任务在 Local 模式下均不承诺可直接续发消息。用户可在目标模式创建新任务并引用旧任务内容。
- 只有未来客户端提供明确、稳定、可验证的跨 Provider 续聊契约，并通过双向真机验收后，才重新评估此能力。

## 后果

模式切换不会破坏历史可读性，也不会为实现续聊而改变用户原始任务。跨模式继续开发需要一个新任务；这是当前版本明确的产品边界，而非待完成的第二阶段。

2026-09-25 复核：确认跨模式查阅旧 Local 项目上下文是产品需求。配置恢复测试应同时验证官方模型与原有设置恢复、活动 Local 路由撤销，以及离线历史 Provider 保留；仅比较恢复后配置与原文是否逐字相同不符合本决策。
