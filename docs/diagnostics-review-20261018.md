## 实施范围

复用 `DiagnosticEvent`、`ModeAwareJsonLineDiagnosticLog`、`JsonLineDiagnosticLog` 和 `DiagnosticSanitizer`，继续由现有“详细日志记录”开关控制。新增 `DiagnosticJournal` 仅负责低频操作的阶段、结果和失败隔离，没有新建轮询器、后台队列、服务或另一套配置。

启动器操作写入原日志目录中的 `launcher.concise.jsonl` / `launcher.full.jsonl`。Agent 与代理保留已有日志文件和请求记录方式，后台新启动及恢复的补充事件使用已有 Agent 写入器。所有新增 JSONL 记录继续使用格式版本 2、事件 ID 和会话 ID；一次操作带有 `operationId`，Agent 写入器已有的 Router 关联信息继续保留。

## 模式与事件

| 操作 | 简易模式 | 详细模式追加 |
| --- | --- | --- |
| 配置载入、保存、另存、应用和卡片预选 | 模型、配置文件名、结果、拦截或错误分类 | 路径、模型类型、绑定读取、资源解析、写入和预选更新阶段及耗时 |
| 用户触发的配置目录扫描 | 预选失效时的关键提示 | 当前候选文件数量；不解析预选菜单 JSON 来增加准入条件 |
| 模板、MTP、视觉、思考和上下文滚动检查 | 添加、检查、复用、移除结果；重复和引用阻止；能力未确认状态 | 原有验证依据的复用或失效情况、原有检测阶段及耗时 |
| 模型管理 | 显示名称、类型、显示/隐藏和列表移除结果 | 保存、引用检查或清理阶段 |
| 本地启动 | 入口、模型、配置、启动检查失败原因 | 配置读取、资源校验、生成 BAT/Router preset/Catalog、已应用快照、Codex 配置和设置提交阶段 |
| 认证 | 保存的选择、请求应用值、成功提交后的应用值 | 对应配置写入阶段；缺字段默认值与显式已存设置来源 |
| 在线恢复、异常回滚、卸载准备 | 是否完成、失败阶段和回滚结果 | 原配置恢复、设置收尾及事务阶段 |

详细模式包含关键结果，但同一事件只写入当时所选模式的文件，不同时写两份。简易模式不记录阶段过程、耗时和异常栈。窗口刷新、悬浮和参数输入不产生日志。

成功请求 Windows 启动客户端记为 `requested`，启动流程完成派发记为 `dispatched`，均不等同于客户端已经完成推理。用户取消、被拦截、资源不可用、操作失败分开记录。验证过程正常完成但能力不支持或未确认，不记录为能力验证通过。

## 数据和安全边界

- 日志使用已经取得的模型 ID、配置文件名、资源文件名、布尔值及结果，不为记录日志重新扫描或加载 GGUF，不重复能力验证。
- 认证设置来源通过原有 settings.json 读取取得元数据，不新增设置文件或第二次文件读取；不将该诊断元数据写入设置。仍使用相同反序列化选项、校验和迁移逻辑。
- 保存的认证偏好不代表当前客户端内存中的实际值。`appliedRequiresOpenAiAuth` 仅在配置与设置提交成功后记录；失败并回滚时不宣称新认证已成功应用。
- 新操作日志不记录整份 JSON、TOML、模板、命令、对话正文或任意异常消息。错误使用静态原因分类、阶段、异常类型和 HRESULT；详细模式增加异常栈，继续经现有脱敏与长度限制处理。
- 日志失败不能改变业务成功结果、原异常或取消结果。新增写入均经过失败隔离；上下文滚动检测已有的原生日志回调也做了同样隔离。
- 沿用既有轮转和容量控制。没有增加 GPU 调用或持续采样。

## 审查中修正的问题

1. **WPF 线程上下文**：最初包装器在等待开始记录后使用后台继续执行，可能让配置载入访问界面控件时发生跨线程异常。已修正为在调用业务委托时保留调用方上下文，底层日志写入仍使用异步 I/O。已在真实 WPF 控件的隔离检查中重新验证载入、保存及应用。
2. **结果准确性**：参数拒绝、重复资源、服务冲突、能力未确认、用户取消和派发启动分别使用对应结果；失败事件即使没有异常对象也标记为 error，避免误记成功。
3. **回滚记录**：保留原失败阶段和回滚完成情况，事务提交失败时不会写入“成功应用认证”的字段。
4. **交互顺序**：配置菜单先显示，再记录扫描结果，避免为了日志而等待文件写入才展开菜单。

修正后未发现未解决的阻断问题。本次没有改变模型参数生成规则、能力验证方法、配置选择语义和 llama.cpp 调用方式。
